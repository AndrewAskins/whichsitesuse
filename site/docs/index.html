// 01  Account and API key

Create an account and get an API key

Every MCP connection and every paid call belongs to an account. Clients that sign in with OAuth, like Claude's and ChatGPT's custom connectors, only need the account, while Claude Code, Cursor and the REST API use an API key.

  1. Go to the sign-up page and enter your email. Use your work email if you want the free credits.
  2. Open the link we email you and press the button on the page it opens. The sign-up link works once and lasts 24 hours, and later sign-in links last 30 minutes. Sign-in is always by emailed link, so there's no password to set.
  3. Once your email is verified, a work email gets 250 credits, once. Personal and free-mail addresses can still sign up and buy credits, they just don't get the free grant, and if you think that call was wrong you can ask for the credits, where a person reads every request. Disposable addresses can't sign up.
  4. If you'll use an API key, create one on your account page. Give it a name, and if you like a monthly credit cap, which stops that key (and any agent using it) from spending more than you set in a calendar month (UTC).
  5. Copy the key straight away. It starts with wsu_live_, it's shown once, and we only keep a hash of it. You can revoke a key or change its cap from the account page at any time.

The free grant is one per person. It's held back when the same inbox already had one on another account, and also when the same device or several accounts from one network got one in the past week. Those last two holds lift on your first purchase.

Send a key as Authorization: Bearer YOUR_API_KEY. The API also accepts the bare key in the Authorization header, or in an x-api-key header, if your client can only set one of those.

// 02  Connect an MCP client

Connect an MCP client

The MCP server is at https://api.whichsitesuse.com/mcp. It uses the Streamable HTTP transport, is stateless and takes POST requests. Every MCP call needs you signed in, either through OAuth or with an API key; without one the server answers 401 and points the client at its OAuth metadata, which is how Claude and ChatGPT know to show you a sign-in.

How signing in works

When a client connects, it registers itself with WhichSitesUse and opens our consent page in your browser. If you're not signed in yet, you sign in or sign up by emailed link first, and the link brings you back to the consent page. The consent page names the app, says it can search and spend credits from your balance but can't see your payment details or buy credits by itself, and lets you set a monthly credit cap for that app. Approve it and you're sent back to the app.

Each approved app shows up on your account page as a connected app, with its usage and cap, and a disconnect button that cuts it off straight away. The app's access token lasts an hour and it renews itself with a refresh token for up to 90 days, so you won't be asked to sign in again unless you disconnect it or it goes 90 days without renewing.

Claude (claude.ai and Claude Desktop)

Go to Customize, then Connectors, choose Add and then Add custom connector. Name it WhichSitesUse, enter https://api.whichsitesuse.com/mcp as the server URL and click Continue. Keep the sign-in option Claude detects. If the dialog asks how Claude identifies itself under OAuth client, choose Register automatically, because WhichSitesUse supports dynamic client registration but not Claude's published identity. Click Add, then Connect, and approve the connection on our consent page. On a Free plan this uses your one custom connector.

On Team and Enterprise plans, an Owner adds the connector under Organization settings, then Connectors, and each member then connects it from Customize, then Connectors, signing in with their own WhichSitesUse account (Anthropic's custom connector docs, checked November 2026). Claude Desktop uses the connectors on your claude.ai account, so there's nothing separate to set up there.

ChatGPT

Custom MCP servers work on ChatGPT on the web, and which plans get them is up to OpenAI. As of November 2026, Business and Enterprise/Edu workspaces get full MCP support, Pro users can connect custom servers with read-only tools, and on Business only admins and owners can add one (OpenAI's help article). Read-only access covers every tool except buy_credits, which ChatGPT treats as a write action because it creates a checkout link.

  1. Go to ChatGPT Plugins, select the plus button, then Add custom MCP server.
  2. Enter WhichSitesUse as the name and, under Connection, https://api.whichsitesuse.com/mcp as the server URL.
  3. Choose OAuth for authentication and leave the client credentials empty, so ChatGPT registers itself.
  4. Review the risk warning, tick I understand and want to continue, then select Create as a plugin and approve the connection on our consent page.
  5. Install the plugin, start a new conversation, type @ and pick WhichSitesUse.

Steps from OpenAI's custom MCP server guide, checked November 2026. ChatGPT asks you to confirm write actions, so expect a prompt before buy_credits runs.

Claude Code

Add the server with an API key from your terminal. Leave out --scope user to add it to the current project only.

claude mcp add --transport http --scope user whichsitesuse \
  https://api.whichsitesuse.com/mcp \
  --header "Authorization: Bearer YOUR_API_KEY"

Cursor

Add the server to ~/.cursor/mcp.json to use it in every project, or to .cursor/mcp.json in one project. Reading the key from an environment variable keeps it out of a file you might commit.

{
  "mcpServers": {
    "whichsitesuse": {
      "url": "https://api.whichsitesuse.com/mcp",
      "headers": {
        "Authorization": "Bearer ${env:WSU_API_KEY}"
      }
    }
  }
}

Other clients and the REST API

Any MCP client that supports remote Streamable HTTP servers can connect, either with OAuth (authorization code with PKCE, discovered from /.well-known/oauth-protected-resource) or with an API key in a request header. Anything that can make an HTTP request can use the REST API at https://api.whichsitesuse.com/v1 with an API key; each operation below shows its REST method and path.

// 03  Requests and responses

Requests and responses

MCP and REST share one definition of each operation, so the field names, limits and costs are the same on both.

Operations

MCP toolRESTCostSign-in needed
find_technologiesGET /v1/technologiesFreeNot on REST
count_sitesGET /v1/countsFreeNot on REST
search_sitesGET /v1/sites1 credit per site returnedYes
lookup_domainGET /v1/domains/:domain2 credits, free when not coveredYes
get_balanceGET /v1/balanceFreeYes
buy_creditsPOST /v1/checkoutFree to callYes

REST paths are relative to https://api.whichsitesuse.com. Over MCP every tool needs you signed in; over REST the two free search tools also answer without a key.

Inputs

On REST, GET operations take their inputs as query parameters and /v1/checkout takes a JSON body. List inputs can be comma-separated (technologies=shopify,klaviyo) or repeated (technologies=shopify&technologies=klaviyo). Over MCP, pass real arrays and objects.

The response envelope

Every successful response, MCP or REST, wraps the result in the same envelope. Over MCP it comes back as the tool's structured content and as JSON text. Keep the attribution line when you publish results.

{
  "data": { ... },
  "meta": {
    "crawl_date": "YYYY-MM-DD",
    "credits_used": 0,
    "credits_remaining": ...,
    "attribution": "Technology data from HTTP Archive (httparchive.org), detected with its open-source Wappalyzer fork. Core Web Vitals from the Chrome UX Report."
  }
}

credits_remaining is your balance after the call, or null for a REST call made without a key. crawl_date is the HTTP Archive crawl the answer came from.

// 04  Operation

find_technologies

Matches a plain name like "hubspot" or a category like "email marketing" to the technologies in the dataset, with each one's slug, categories, a note where two products share a name, and how many sites use it. Call it first, then pass the slugs to the other tools. Free, and on REST it works without a key.

Inputs

FieldType and limitsNotes
qstring, 1 to 100 characters, requiredA technology or category in plain words. Spaces and punctuation are ignored, so "Word Press" finds WordPress.
limitinteger, 1 to 50, default 10Most matches to return.

Exact name or alias matches come first, then names that start with your words, then names that contain them, then category matches. Ties go to the technology on more sites.

Request

REST: GET /v1/technologies

curl "https://api.whichsitesuse.com/v1/technologies?q=hubspot&limit=5"

Response

{
  "data": {
    "matches": [
      {
        "tech_id": ...,
        "name": "...",
        "slug": "...",
        "categories": ["..."],
        "vendor_domain": "example.com",
        "note": "..." | null,
        "site_count": ...
      }
    ]
  },
  "meta": { "crawl_date": "YYYY-MM-DD", "credits_used": 0, ... }
}

Slugs are usually the name in lower case with hyphens, but take them from this tool rather than guessing.

// 05  Site filters

Site filters

count_sites and search_sites share one filter definition, so a count always matches the list it prices. Pass technologies, category or both; the other fields narrow the result.

FieldType and limitsNotes
technologieslist of up to 20 slugs, each 1 to 100 charactersSlugs from find_technologies, such as ["shopify","klaviyo"].
match"all" or "any", default "all""all" needs every listed technology on the site, "any" needs at least one.
exclude_technologieslist of up to 20 slugsDrops sites that use any of these. A slug can't be both required and excluded.
categorystring, 1 to 100 charactersA technology category such as "Email marketing", case-insensitive. A site matches if it uses any technology in it.
versionstring, 1 to 50 charactersA version prefix for the matched technologies: "6.8" matches 6.8.1 but not 60.1.
rank_bucketslist of up to 20 positive integers or "unknown"Chrome UX Report popularity buckets as count_sites returns them: 1000 is the top 1k, 5000 is 1k to 5k, 500000 is 100k to 500k.
max_rankpositive integerOnly sites in the top N, such as 100000 for the top 100k. Sites with an unknown rank are dropped.
tldlist of up to 50, each 1 to 30 charactersTop-level domains such as ["com","co.uk"]. A leading dot is ignored.
cwvobject with lcp, inp and cls, each "pass" or "fail"Core Web Vitals at the 75th percentile. Pass means at or under Google's good threshold (LCP 2,500 ms, INP 200 ms, CLS 0.1). Sites without field data match neither. REST: cwv=lcp:fail,inp:pass.
device"mobile", "desktop" or "any", default "any"With mobile or desktop, the technologies must be detected on that device and CWV uses that device's field data. With any, either device counts and CWV uses mobile.

An unknown slug or category is an invalid_input error that names it, and for slugs lists them in unknown_technologies, so an agent can look them up and retry.

// 06  Operation

count_sites

Counts the sites that match a filter, split by popularity bucket, and says what the full list would cost in full_list_credits. Free, and on REST it works without a key, so call it before search_sites to size and price a list.

Inputs

The site filters, nothing else.

Request

REST: GET /v1/counts

curl "https://api.whichsitesuse.com/v1/counts?technologies=wordpress&max_rank=1000000&cwv=inp:fail"

Response

{
  "data": {
    "total": ...,
    "by_rank_bucket": [
      { "rank_bucket": 1000, "sites": ... },
      { "rank_bucket": 5000, "sites": ... },
      { "rank_bucket": null, "sites": ... }
    ],
    "full_list_credits": ...
  },
  "meta": { "crawl_date": "YYYY-MM-DD", "credits_used": 0, ... }
}

Buckets run from most popular to least, and null (unknown rank) comes last. full_list_credits equals total, because each site in a list costs one credit.

// 07  Operation

search_sites

Lists the sites that match a filter, best-ranked first, with the technologies that matched (versions and first and last seen dates) and a Core Web Vitals summary for each. Costs 1 credit per site returned.

Inputs

The site filters, plus:

FieldType and limitsNotes
limitinteger, 1 to 1000, default 100Most sites to return in this call.
max_creditsinteger, 0 or moreMost credits this call may spend. The call returns fewer sites rather than spend more.
cursorstring, 1 to 1000 charactersnext_cursor from the previous page, unchanged.

A page holds the smallest of limit, your balance, max_credits, what's left under the key's monthly cap, and 100 for accounts that haven't paid yet. If that comes to zero you get an insufficient_credits error with checkout links instead of an empty page, unless you passed max_credits: 0, which returns no sites, costs nothing and hands back the same cursor.

Request

REST: GET /v1/sites

curl "https://api.whichsitesuse.com/v1/sites?technologies=shopify&max_rank=100000&tld=com&limit=100&max_credits=100" \
  -H "Authorization: Bearer $WSU_API_KEY"

Response

{
  "data": {
    "sites": [

        "root_url": "https://example.com/",
        "rank_bucket": ... | null,
        "tld": "com",
        "technologies": [
          {
            "name": "...",
            "slug": "...",
            "version": "..." | null,
            "first_seen": "YYYY-MM-DD",
            "last_seen": "YYYY-MM-DD",
            "confidence": ...
          }
        ],
        "cwv": {
          "device": "mobile",
          "lcp": { "p75": ... | null, "pass": true | false | null },
          "inp": { "p75": ... | null, "pass": true | false | null },
          "cls": { "p75": ... | null, "pass": true | false | null }

Sites are ordered by popularity bucket, then by domain. next_cursor is null on the last page. LCP and INP are in milliseconds and CLS has no unit; pass is null when the site has no field data.

// 10  Operation

buy_credits

Creates a checkout link for a top-up or a monthly plan. An agent can't pay, so it gives the link to the person it works for, who opens it and pays by card through Stripe. Free to call; nothing is charged until a person pays.

Inputs

FieldType and limitsNotes
item"topup", "starter", "growth", "pro" or "scale", requiredA top-up is $15 per 1,000 credits and lasts 12 months. The plans are listed under credits and billing.
unitsinteger, 1 to 100, default 1Top-ups only: how many blocks of 1,000 credits.

Request

REST: POST /v1/checkout

curl -X POST "https://api.whichsitesuse.com/v1/checkout" \
  -H "Authorization: Bearer $WSU_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"item": "topup", "units": 5}'

Response

{
  "data": {
    "checkout_url": "https://.../buy/...",
    "item": "topup",
    "label": "5,000 credits (top-up)",
    "price": "$75",
    "credits": 5000,
    "next_step": "Give checkout_url to the person you're working for. It opens a secure Stripe checkout and stays valid for 7 days."
  },
  "meta": { "credits_used": 0, ... }
}

A checkout link only pays into the account it was made for and grants nothing else, so it's safe to pass to whoever holds the card. If the account already has a plan, a plan link sends the owner to sign in and change it from billing instead, so nobody pays for two plans. Top-up links always work.

Credits and billing

A site in a list costs one credit and a domain lookup costs two. Counts, technology search, balance checks, checkout links and "not covered" lookups are free.

Top-ups are $15 per 1,000 credits, up to 100 blocks in one checkout, and last 12 months. You can buy them on any plan or with no plan at all.

Monthly reset and spend order

Plan credits arrive when each monthly invoice is paid and don't roll over: whatever's left goes when the next month's credits land. Spending takes plan credits first, then top-up credits, then the free grant. If you cancel a plan, the credits you already have last until the end of that billing month.

Plans are changed or cancelled from the billing link on your account page, which opens Stripe's billing portal with your invoices and payment details.

When credits run out

A call is charged after it runs, for what it actually returned, and meta.credits_remaining shows the balance afterwards. When a paid call can't be covered, it fails with HTTP 402 and the code insufficient_credits, and nothing is charged. The error says how many credits the call needed, how many were available, how many it was short, and why, in reason:

reasonWhat it meansWhat to do
balanceThe account is out of credits.Open one of the checkout links in options: a top-up that covers the shortfall, or the smallest plan that covers the call. Links last 7 days.
max_creditsThe call's max_credits is lower than its cost.Raise max_credits or narrow the request.
key_capThis key or connected app has reached its monthly cap.The account owner can raise the cap on the account page.

// 12  Errors

Errors

Errors have the same body on REST and MCP: {"error": {"code", "message", ...details}}. REST sets the HTTP status below; MCP returns the same JSON as a tool result marked as an error.

CodeHTTPWhen
invalid_input400A field is missing or invalid, or a slug, category, domain or cursor isn't recognised. issues lists each field and what's wrong with it.
unauthorized401A REST call to a paid or account operation had no key, or the key is invalid or revoked; a missing key also gets a signup_url. Over MCP, a request without a valid OAuth token or key gets HTTP 401 with a WWW-Authenticate header before any tool runs.
insufficient_credits402The call can't be covered by the balance, max_credits or the key's cap. See credits and billing.
account_suspended403The account is suspended. Reply to any WhichSitesUse email to sort it out.
not_found404No such endpoint.
rate_limited429Too many calls this minute. Includes retry_after_seconds and limit_per_minute, and REST also sends a Retry-After header.
internal500Something went wrong on our side.
billing_unavailable503Accounts can't be checked on the server right now.
snapshot_unavailable503The monthly dataset is loading. Try again in a few minutes.

Rate limits and trial limits

Limits count calls in one-minute windows. Signed-in calls count against the account, so every key and connected app on it shares one limit.

CallerCalls a minuteCounted per
No key (REST find_technologies and count_sites only)30IP address

Until an account's first purchase, a call also returns at most 100 results, whatever limit says. Both limits lift as soon as the account pays for a plan or a top-up. The sign-up and sign-in forms send at most 10 emails an hour from one IP address.

// 14  Data

Data freshness and coverage

Every answer comes from a monthly snapshot of HTTP Archive's public crawl, which tests the homepage and one inner page of about 15 million sites that real Chrome users visit. Technologies are detected with HTTP Archive's fork of the Wappalyzer rules, and Core Web Vitals are Chrome UX Report field data from the newest month at or before the crawl.

We load each crawl once HTTP Archive has finished publishing it, so a result can be up to about six weeks old. meta.crawl_date tells you which crawl you're looking at, and first_seen and last_seen on each technology are the first and latest crawls in which we saw it on that site. Our history starts with our first snapshot, so first_seen can be later than the day a site really added something.

Sites with little Chrome traffic are often missing from the crawl, and a lookup on one says "not covered" and costs nothing. Detection only sees what loads on public pages, so tools that live behind a login, like a CRM's back office or payroll software, don't show up. A site that blocks the crawler or loads a tool only after some interaction may also look like it doesn't use it. The data has no company firmographics, contacts or emails.
